## 1. Kavramsal Temel — Neden Var?

NTLM relay saldırısının temel hilesi basittir: saldırgan, bir kurbanın kimlik doğrulamasını **yakalar** ve onu **başka bir sunucuya aynen iletir (relay)**. Kurban DC'ye yetkiliyse, saldırgan o yetkiyle DC'ye LDAP bağlanır ve nesneleri değiştirir (örn. RBCD kurar, DCSync hakkı ekler → [Blue M06](../Modul_06_Kerberos_ve_Delegation_Sertlestirme/), [Blue M05](../Modul_05_Yetki_ve_ACL_Sikilastirma/)). Bu saldırının işe yaramasının nedeni, oturumun **bütünlük ve bağlam kontrolü** olmamasıdır — sunucu, kimlik doğrulamanın "aradaki biri tarafından iletilip iletilmediğini" anlayamaz.

İki koruma bunu kırar:
- **LDAP Signing:** LDAP oturumunun **imzalanmasını** zorlar → iletilen (relay) trafik imza tutmaz, reddedilir.
- **Channel Binding (LDAPS için EPA — Extended Protection for Authentication):** Kimlik doğrulamayı, üzerinden geçtiği **TLS kanalına bağlar** → başka bir kanala relay edilemez.

> **İlke:** Relay, kimlik doğrulamayı "bağlamından koparıp" başka yere taşımaktır. Signing bütünlüğü, Channel Binding kanal-bağlamını zorlar — ikisi de "bu auth başka yere taşınamaz" der.

Bu, [Sistem 10.3 Hardening](../../1-Sistem_Yoneticisi/Modul_10_Guvenlik_Yedekleme_ve_Kurtarma/10.3_Hardening_Temelleri.md)'in "LDAP/SMB signing" temelinin derinleştirilmiş, relay-odaklı uygulamasıdır.

## 2. Teknik Derinlik

### 2.1 LDAP relay akışı ve iki savunma noktası

```
   Kurban (DC'ye yetkili)      Saldırgan (relay)          DC (LDAP)
      │  ① koersiyon/poison       │                          │
      │  ile auth başlar          │                          │
      │──────────────────────────►│  ② auth'u DC'ye İLET      │
      │                           │─────────────────────────►│  ③ LDAP bağlan
      │                           │  (kurbanın yetkisiyle)    │     → RBCD/DCSync ekle
      │                           │                          │
   ✗ SIGNING açıksa: iletilen oturum imza tutmaz → DC REDDEDER (② kırılır)
   ✗ CHANNEL BINDING (LDAPS/EPA): auth TLS kanalına bağlı → başka kanala relay ✗
```

### 2.2 LDAP Signing seviyeleri

`Domain controller: LDAP server signing requirements` politikası üç değerdedir:
- **None:** imza istenmez (relay'e açık — kötü).
- **Negotiate signing:** istemci desteklerse imzala (yeterli değil — istemci "imzasız" derse kabul).
- **Require signing:** imza **zorunlu** → imzasız/relay oturum reddedilir (hedef).

Kritik: yalnızca "Require" gerçek korumadır; "Negotiate" bir saldırganın imzayı düşürmesine (downgrade) izin verir.

### 2.3 Channel Binding ve LDAPS

LDAP Signing, **LDAP over TLS (LDAPS, 636)** için tam koruma sağlamaz — imza TLS'in altında olduğundan. Bunun için **Channel Binding Token (CBT / EPA)** gerekir: kimlik doğrulama, TLS oturumunun parmak iziyle **mühürlenir**. `LdapEnforceChannelBinding` registry değeriyle zorlanır. LDAP signing (389) + Channel Binding (636) **birlikte** tüm LDAP relay yüzeyini kapatır.

## 3. Pratik Uygulama

### 3.1 LDAP Signing'i zorunlu yap (DC'lerde)
```text
GPO (Domain Controllers'a link): Computer Config → Windows Settings →
  Security Settings → Local Policies → Security Options →
   "Domain controller: LDAP server signing requirements" = Require signing
   "Network security: LDAP client signing requirements"  = Require signing
```

### 3.2 Channel Binding'i etkinleştir (LDAPS/EPA)
```powershell
# DC'de LDAP Channel Binding zorla (2 = Always/Require)
New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\NTDS\Parameters" `
  -Name LdapEnforceChannelBinding -Value 2 -PropertyType DWORD -Force
# (Önce 1 = "when supported" ile uyumluluğu test et, sonra 2)
```

### 3.3 Mevcut durumu doğrula (audit)
```powershell
# LDAP signing gerektiriliyor mu? (event 2889 imzasız bağlantıları raporlar)
Get-WinEvent -FilterHashtable @{LogName='Directory Service'; Id=2889} -MaxEvents 50 |
  Select TimeCreated, @{N='ImzasizIstemci';E={$_.Message.Split("`n")[1]}}
# 2889 = imzasız/uyumsuz LDAP bind → "Require" öncesi bu istemcileri düzelt
```

## 7. Güvenlik Notu ve Sık Yapılan Hatalar

- 🔴 **"Negotiate" ile yetinmek:** Yalnızca "Require signing" gerçek korumadır; Negotiate downgrade'e izin verir.
- 🔴 **LDAPS'i signing ile koruduğunu sanmak:** LDAP signing 636'yı tam korumaz; Channel Binding (EPA) ayrıca gerekir — ikisi birlikte.
- ⚠️ **"Require"a doğrudan geçmek:** 2889 üreten uyumsuz istemciler (eski cihaz/uygulama) kırılır; önce audit (2889) ile tespit et, düzelt, sonra zorla.
- ⚠️ **LdapEnforceChannelBinding'i test etmeden 2 yapmak:** Önce 1 ("when supported") ile uyumluluğu ölç, sonra 2 (Always).
- 🔍 **İzleme ipucu:** 2889 olaylarının **kaynak istemcileri**, hem relay yüzeyini hem de eski/riskli sistemleri gösterir — düzenli sıfırlanması gereken bir teknik borç listesidir.
