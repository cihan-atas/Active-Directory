## 1. Kavramsal Temel — Neden Var?

AD CS (Active Directory Certificate Services), kimlik doğrulama için sertifika dağıtır ([Sistem 07.2](../../1-Sistem_Yoneticisi/Modul_07_PKI_ve_Sertifika_Servisleri/07.2_Sertifika_Sablonlari_ve_Izinler.md)). 2021'de SpecterOps'un "Certified Pre-Owned" araştırması, yanlış yapılandırılmış sertifika şablonlarının **domain ele geçirmeye giden bir otoyol** olduğunu gösterdi: **ESC1-ESC8** olarak adlandırılan zafiyet sınıfları. Temel fikir yıkıcı derecede basit: eğer düşük yetkili bir kullanıcı, **başka biri (örn. Domain Admin) adına** sertifika alabiliyorsa, o sertifikayla DA olarak kimlik doğrulaması yapar. Sertifika, parola/hash gerektirmez ve **uzun ömürlüdür** — mükemmel kalıcılık.

Savunmanın kalbi, **şablon izinlerinin ve ayarlarının denetimidir**: hangi şablon "enrollee supplies subject" (ESC1), hangisi zayıf enrollment izni veriyor, hangisi tehlikeli EKU (Client Authentication) taşıyor? Bu denetim saldırgandan **önce** yapılmalı; çünkü Certipy/Certify ([Red M07](../../3-Red_Team/Modul_07_AD_CS_PKI_Saldirilari/)) bunları saniyeler içinde bulur.

> **İlke:** Bir kullanıcı "başkası adına" kimlik doğrulama sertifikası alabiliyorsa, o kullanıcı zaten o kişidir. Şablon izinlerini ve SAN ayarlarını **ayrıcalık yükseltme yolu** gibi denetle.

Bu, [Sistem 07.2](../../1-Sistem_Yoneticisi/Modul_07_PKI_ve_Sertifika_Servisleri/07.2_Sertifika_Sablonlari_ve_Izinler.md)'nin şablon yönetiminin güvenlik denetimidir.

## 2. Teknik Derinlik

### 2.1 ESC zafiyet haritası (özet)

```
   ESC   KOŞUL                                          SONUÇ
   ───   ─────                                          ─────
   ESC1  Enrollee supplies subject (SAN) + Client Auth  başkası adına sertifika → DA
         EKU + düşük enroll izni
   ESC2  Any Purpose / SubCA EKU                         her amaç için kötüye kullanım
   ESC3  Enrollment Agent şablonu                        başkası adına talep (agent)
   ESC4  Şablon üzerinde yazma hakkı (DACL)              şablonu ESC1'e çevir
   ESC5  PKI nesnelerinde zayıf ACL (CA, NTAuthCert)     PKI'yı ele geçir
   ESC6  CA'da EDITF_ATTRIBUTESUBJECTALTNAME2            her talebe SAN ekle (07.2)
   ESC7  CA yönetim izni (ManageCA/Certificates)         talep onayla/şablon aç
   ESC8  HTTP enrollment (web enrollment) + NTLM relay   relay ile sertifika (08)
```

### 2.2 ESC1'in anatomisi (en yaygın)

Bir şablon şu üçünü aynı anda taşıyorsa ESC1'dir:
1. **`msPKI-Certificate-Name-Flag` = ENROLLEE_SUPPLIES_SUBJECT (0x1):** Talep eden, sertifikadaki SAN'ı (kimin adına?) kendisi belirler.
2. **EKU: Client Authentication** (veya PKINIT/Smart Card Logon): sertifika **kimlik doğrulaması** için kullanılabilir.
3. **Düşük yetkili gruba `Enroll` izni** (örn. Domain Users) + **manager approval kapalı**.

Sonuç: `Domain Users` bir üyesi, SAN'a `Administrator@corp.local` yazıp Client Auth sertifikası alır ve DA olarak PKINIT ile oturum açar.

### 2.3 Neden bu kadar tehlikeli?

Sertifika **parola değişiminden etkilenmez** ve **uzun ömürlüdür** (yıllar). krbtgt reset bile ([Blue M10](../Modul_10_Olay_Mudahalesi_DFIR_ve_Kurtarma/)) sertifikayı geçersizleştirmez — iptal (revocation) veya süre dolumu gerekir. Bu yüzden AD CS kalıcılığı ([07.3](./07.3_Sertifika_Tabanli_Kalicilik_Tespiti.md)) çok sinsidir.

## 3. Pratik Uygulama

### 3.1 Zafiyet taraması (Certipy — savunma amaçlı)
```bash
# Certipy ile tüm ESC zafiyetlerini denetle (kendi ortamında, yetkiyle)
certipy find -u blueteam@corp.local -p '***' -dc-ip 10.0.0.1 -vulnerable -stdout
# → ESC1-8 bulgularını listeler; her [!] Vulnerable bir düzeltme kaydıdır
```

### 3.2 ESC1 şablonlarını PowerShell ile bul
```powershell
# Enrollee-supplies-subject + Client Auth EKU + geniş enroll = ESC1 adayı
Get-ADObject -SearchBase "CN=Certificate Templates,CN=Public Key Services,CN=Services,$((Get-ADRootDSE).configurationNamingContext)" `
  -LDAPFilter "(objectClass=pKICertificateTemplate)" `
  -Properties msPKI-Certificate-Name-Flag, pKIExtendedKeyUsage, nTSecurityDescriptor |
  Where-Object { ($_.'msPKI-Certificate-Name-Flag' -band 1) -and    # ENROLLEE_SUPPLIES_SUBJECT
                 ($_.pKIExtendedKeyUsage -contains '1.3.6.1.5.5.7.3.2') } |  # Client Auth
  Select Name, msPKI-Certificate-Name-Flag
```

### 3.3 Düzeltme (ESC1'i kapat)
```text
certtmpl.msc → şablon → Properties →
  • Subject Name sekmesi: "Build from this AD information" (ENROLLEE_SUPPLIES_SUBJECT kaldır)
  • Security: Enroll iznini yalnızca gerekli gruba ver (Domain Users KALDIR)
  • Issuance Requirements: "CA certificate manager approval" (manager approval AÇ)
→ Değişikliği yayınla; eski hatalı şablonu CA'dan kaldır.
```

## 4. Tespit Değeri — Kötüye Kullanım İzleri

Şablonu düzeltmek en iyisidir; ama sömürü anını da yakala:

```yaml
# Sigma — ESC1 sömürüsü: SAN içeren sertifika talebi (başkası adına)
title: AD CS ESC1 Sup­heli Sertifika Talebi (SAN ile)
logsource: { product: windows, service: security }
detection:
  sel:
    EventID: 4886       # certificate services received request
  san_request:
    EventID: 4887       # certificate issued (SAN mismatch izlenmeli)
  condition: sel or san_request
level: high
tags: [attack.privilege_escalation, attack.persistence, attack.t1649]
```
```powershell
# Get-WinEvent — CA'da sertifika talep/verme olayları (4886/4887/4888)
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4886,4887} |
  Select TimeCreated, Id, @{N='Detay';E={$_.Message.Split("`n")[0]}}
# Requester != Subject/SAN (başkası adına) → ESC1 sömürü işareti
```

| Sinyal | Event (CA) | Anlamı | MITRE |
|--------|-----------|--------|-------|
| Sertifika talebi + SAN | 4886 | ESC1 sömürü hazırlığı | T1649 |
| Sertifika verildi (SAN≠requester) | 4887 | Başkası adına sertifika | T1649 |
| Şablon DACL değişimi | 5136 | ESC4 (şablonu ESC1 yapma) | T1649 |
| PKINIT ile anormal logon | 4768 (PKINIT) | Sertifikayla kimlik doğrulama | T1649 |

## 5. Doğrulama / Lab

```powershell
# 1) Envanter kanıtı: certipy find -vulnerable → hiç ESC1-8 bulgusu OLMAMALI
# 2) Sömürü testi (izole lab): kasıtlı ESC1 şablonu kur → certipy req ile
#    Administrator adına sertifika al → §4 4886/4887 alarmı çıkmalı → şablonu düzelt
Invoke-AtomicTest T1649 -TestNumbers 1   # sertifika kötüye kullanımı → CA olayları
# 3) Düzeltme kanıtı: şablonu düzelt → certipy find tekrar → bulgu kaybolmalı
```
> **Kanıt:** İki ölçüt — (a) `certipy find -vulnerable` boş, (b) ESC1 sömürüsü CA olaylarında (4886/4887) yakalanıyor. Şablon düzeltilince zafiyet ortadan kalkmalı.

## 7. Güvenlik Notu ve Sık Yapılan Hatalar

- 🔴 **Şablonları hiç denetlememek:** ESC1-8 çoğu ortamda varsayılan/eski şablonlarda gizlidir; `certipy find -vulnerable` ile düzenli tara.
- 🔴 **`Domain Users`'a Client Auth + SAN şablonuna enroll vermek:** Klasik ESC1; enroll iznini daralt, ENROLLEE_SUPPLIES_SUBJECT kaldır, manager approval aç.
- ⚠️ **Şablon DACL'ini unutmak (ESC4):** Şablona yazabilen biri onu ESC1'e çevirir; şablon nesnelerini [05.2](../Modul_05_Yetki_ve_ACL_Sikilastirma/05.2_Tehlikeli_DACL_Denetimi_ve_Temizligi.md) DACL denetimine dahil et.
- ⚠️ **CA olay denetimini açmamak:** 4886/4887 (talep/verme) yoksa sömürü görünmez; CA'da audit'i etkinleştir ([07.4](./07.4_PKI_Izleme_ve_Olay_Kayitlari.md)).
- 🔍 **İzleme ipucu:** Requester ile sertifikadaki SAN'ın uyuşmaması (bir kullanıcının **başkası** adına sertifikası) ESC1'in doğrudan izidir — kritik alarm.
