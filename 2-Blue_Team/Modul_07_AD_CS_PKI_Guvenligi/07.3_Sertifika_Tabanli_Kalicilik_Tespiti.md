## 1. Kavramsal Temel — Neden Var?

Sertifika tabanlı saldırıların en sinsi yanı **kalıcılıktır (persistence)**. Bir parola/hash çalındığında savunma yanıtı basittir: parolayı değiştir, krbtgt'yi resetle. Ama saldırgan geçerli bir **kimlik doğrulama sertifikası** aldıysa, bu sertifika **parola değişiminden bağımsız olarak yıllarca geçerlidir**. Kullanıcı parolasını değiştirse, hesap Protected Users'a girse, krbtgt iki kez resetlense bile — sertifika hâlâ çalışır. Tek çözüm: sertifikayı **iptal etmek (revoke)** veya süresinin dolmasını beklemek.

İki temel kalıcılık biçimi:
- **Çalınan/forge sertifika:** ESC1-8 ([07.1](./07.1_Sertifika_Sablonu_Izin_Denetimi_ESC.md)) ile alınan uzun ömürlü kimlik sertifikası.
- **Shadow Credentials:** Hedef hesabın `msDS-KeyCredentialLink` özniteliğine saldırganın kontrolündeki bir **anahtar** (Key Trust/WHfB) yazılır → saldırgan o hesap için PKINIT ile bilet alır, parolayı hiç bilmeden.

> **İlke:** Sertifika parola değişimini umursamaz. Çalınan bir sertifika, tespit edilip **iptal edilmedikçe** yıllarca açık bir arka kapıdır. Kalıcılığı sertifika/anahtar düzeyinde ara.

Bu, [Sistem 07.4 Sertifika Yaşam Döngüsü](../../1-Sistem_Yoneticisi/Modul_07_PKI_ve_Sertifika_Servisleri/07.4_Sertifika_Yasam_Dongusu.md)'nün (iptal/yenileme) güvenlik karşılığıdır ve [Blue M10 IR](../Modul_10_Olay_Mudahalesi_DFIR_ve_Kurtarma/)'a besleme yapar.

## 2. Teknik Derinlik

### 2.1 Shadow Credentials mekaniği (msDS-KeyCredentialLink)

```
   Saldırgan hedef hesap üzerinde WRITE hakkına sahip (GenericWrite/GenericAll)
        │  → [Blue 05.2 DACL hijyeni]
        ▼
   Hedefin msDS-KeyCredentialLink'ine kendi ürettiği açık anahtarı YAZAR
        │  (Whisker / pyWhisker / Certipy shadow)
        ▼
   PKINIT ile hedef adına TGT alır (anahtarın özel yarısıyla)
        │
        ▼
   Parola/hash hiç gerekmedi → hesabın NT hash'ini de alır (UnPAC-the-hash)
   Kalıcılık: link silinene kadar saldırgan istediğinde bilet üretir.
```

### 2.2 Neden krbtgt reset işe yaramaz?

Golden Ticket krbtgt hash'ine dayanır; krbtgt reset onu keser. Ama sertifika/Shadow Credentials **krbtgt'den bağımsızdır** — PKINIT, sertifikanın/anahtarın kendi güven zincirini kullanır. Bu yüzden AD CS kalıcılığı, klasik IR adımlarını (parola/krbtgt reset) **atlatır**; ayrı bir tespit ve temizlik (iptal + link temizleme) gerekir.

### 2.3 Sertifika ömrü ve iptal (revocation)

Bir kimlik sertifikası genelde 1-2 yıl geçerlidir. İptal, sertifikayı **CRL/OCSP**'ye ([Sistem 07.3](../../1-Sistem_Yoneticisi/Modul_07_PKI_ve_Sertifika_Servisleri/07.3_Autoenrollment_CRL_OCSP.md)) ekler; ama PKINIT bazı yapılandırmalarda CRL'i katı kontrol etmez — bu yüzden sertifikayı iptal etmek **her zaman yeterli olmayabilir**, kaynak zafiyet (şablon/CA) da kapatılmalı.

## 3. Pratik Uygulama

### 3.1 Shadow Credentials avı (msDS-KeyCredentialLink)
```powershell
# Beklenmedik msDS-KeyCredentialLink taşıyan hesaplar (WHfB kullanmayan ortamda = şüphe)
Get-ADObject -LDAPFilter "(msDS-KeyCredentialLink=*)" `
  -Properties msDS-KeyCredentialLink, samAccountName |
  Where-Object { $_.samAccountName -notmatch '^DC' } |   # DC'ler meşru olabilir
  Select samAccountName, @{N='KeyLinkSayisi';E={$_.'msDS-KeyCredentialLink'.Count}}
# WHfB kullanılmıyorsa herhangi bir link şüphelidir → araştır
```

### 3.2 Verilmiş sertifikaları denetle (CA veritabanı)
```powershell
# CA'da verilmiş sertifikaları listele (anormal SAN / şablon / requester ara)
certutil -view -restrict "Disposition=20" -out "RequesterName,CommonName,NotAfter,CertificateTemplate" csv
# Requester != Subject, uzun NotAfter, hassas hesap adına = kalıcılık işareti
```

### 3.3 Kalıcılığı temizle (iptal + link silme)
```powershell
# 1) Şüpheli Shadow Credential linkini kaldır
Set-ADObject -Identity "CN=victim,..." -Clear "msDS-KeyCredentialLink"
# 2) Kötüye kullanılan sertifikayı iptal et (CA'da)
certutil -revoke <SerialNumber> 4     # reason 4 = superseded / uygun sebep
certutil -crl                          # CRL'i yeniden yayınla
```

## 4. Tespit Değeri — Sigma / KQL

```yaml
# Sigma — Shadow Credentials: msDS-KeyCredentialLink değişimi
title: Shadow Credentials - msDS-KeyCredentialLink Yazimi
logsource: { product: windows, service: security }
detection:
  sel:
    EventID: 5136
    AttributeLDAPDisplayName: 'msDS-KeyCredentialLink'
    OperationType: '%%14674'          # value added
  condition: sel
level: high
tags: [attack.persistence, attack.credential_access, attack.t1556.004, attack.t1649]
```
```powershell
# Get-WinEvent — msDS-KeyCredentialLink yazımı (kim, hangi hedef)
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=5136} |
  Where-Object { $_.Message -match 'msDS-KeyCredentialLink' } |
  Select TimeCreated, @{N='Kim';E={($_.Message -split 'Account Name:\s+')[1].Split("`n")[0]}},
                      @{N='Hedef';E={($_.Message -split 'DN:\s+')[1].Split("`n")[0]}}
```

## 7. Güvenlik Notu ve Sık Yapılan Hatalar

- 🔴 **Parola/krbtgt reset'i yeterli sanmak:** Sertifika/Shadow Cred bunlardan bağımsızdır; ayrıca iptal + link temizliği + kaynak zafiyet kapatma gerekir.
- 🔴 **msDS-KeyCredentialLink'i izlememek:** WHfB kullanılmayan ortamda buraya yazma neredeyse her zaman Shadow Credentials'tır; 5136 ile izle.
- ⚠️ **Sadece iptal edip kaynağı bırakmak:** Sertifika iptal edilse de ESC şablonu açıksa saldırgan yenisini alır; kaynağı ([07.1](./07.1_Sertifika_Sablonu_Izin_Denetimi_ESC.md)/[07.2](./07.2_CA_Hardening_ve_ESC6.md)) da kapat.
- ⚠️ **PKINIT CRL kontrolünü zayıf bırakmak:** İptal edilen sertifika hâlâ kabul ediliyorsa kalıcılık sürer; strong mapping (KB5014754) ve CRL kontrolünü sıkılaştır.
- 🔍 **İzleme ipucu:** Parola reset sonrası hâlâ başarılı **PKINIT (sertifika) 4768'leri** üreten bir hesap, klasik IR'ı atlatan sertifika kalıcılığının kesin işaretidir → [Blue M10](../Modul_10_Olay_Mudahalesi_DFIR_ve_Kurtarma/).
